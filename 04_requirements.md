# 04. Requirements.md

## 1. Область действия (Scope)
Документ описывает требования к системе кредитного скоринга и принятия решений (далее — Система). Система автоматизирует рассмотрение заявок на потребительский кредит для физических лиц. В текущей версии поддерживается один продукт — `prod_standard` (см. Ограничение 2).

## 2. Функциональные требования (FR)

### 2.1. Приём и валидация заявки
*   **FR-01 (Приём):** Система должна принимать заявки через API (`POST /applications`). Входные данные: `age`, `income`, `employment`, `family`, `amount`, `term`.
*   **FR-02 (Валидация):** Система должна валидировать обязательность полей и формат данных до отправки во внешние сервисы: `passport_hash` (16 hex-символов), `amount` (10 000–1 000 000 по продукту; формат API допускает до 5 000 000, суммы выше 1 000 000 отклоняются с `AMOUNT_OUT_OF_RANGE`), `term` (3–60 мес.). При ошибке — возвращать `Error` (HTTP 422 Unprocessable Entity, схема `Error`).

### 2.2. Внешние интеграции (БКИ, СМЭВ)
*   **FR-03 (БКИ):** Система должна запрашивать кредитную историю в БКИ. Запрос асинхронный, с таймаутом `3000` мс. Результат сохраняется в `ExternalRequest`.
*   **FR-04 (СМЭВ):** Система должна проверять данные через СМЭВ (например, действительность паспорта). Результат — статус `MATCH / MISMATCH / TIMEOUT / NOT_CALLED`.

### 2.3. Скоринг и принятие решения
*   **FR-05 (Скоринг):** Система должна рассчитывать `score` как сумму баллов по 5 признакам (доход, занятость, возраст, семья, БКИ) в диапазоне 0–100, порог одобрения — 60.
*   **FR-06 (Лимиты):** Система должна рассчитывать одобренный лимит (`amount_approved`) на основе скоринга и коэффициента долговой нагрузки DTI.
*   **FR-07 (Решение):** Система должна формировать решение (`decision`: `APPROVED` / `REFUSED` / `NEED_MORE_DATA` / `MANUAL_REVIEW`) и причину (`reason`).
*   **FR-08 (Аудит):** Каждое действие (запрос, решение, пересчёт) должно логироваться в аудит с 8 полями: `event_id`, `app_id`, `action`, `decision`, `reason`, `score`, `actor`, `at` (подробнее — в ИБ.md, п. 3).

### 2.4. Лимиты и эмуляторы
*   **FR-09 (Эмуляторы):** Система должна поддерживать механизм эмуляторов (симуляторов) для тестирования сценариев без реальных запросов в БКИ/СМЭВ.
*   **FR-10 (Нагрузка):** Система должна проверять текущую кредитную нагрузку клиента (через БКИ) перед одобрением.

## 3. Нефункциональные требования (NFR)

*   **NFR-01 (Таймауты):** Время ответа Системы на запрос `GET /applications/{id}/decision` не должно превышать `3000` мс (p95). Таймаут внешних запросов (БКИ/СМЭВ) — `3000` мс.
*   **NFR-02 (Доступность):** Доступность сервиса — `99.9%` (SLA).
*   **NFR-03 (Маскирование):** `passport_hash` не логируется; `income` в логах заменяется на `***`. Прочие персональные данные в логах и ответах API маскируются (например, `Иванов И.И.`, `+7***123-45-67`).
*   **NFR-04 (Аудит):** Все события доступа к PII должны фиксироваться в неизменяемом логе (WORM).
*   **NFR-05 (Отсутствие дискриминации):** Скоринговая модель не должна использовать признаки пола, национальности, расы, религии (проверяется на этапе валидации модели).
*   **NFR-06 (Объяснимость):** Каждое решение содержит `reason` (машинный код) и человекочитаемый текст для клиента (каталог — 08_reasons_sdel.md).

## 4. Ограничения (Constraints)

*   **Ограничение 1 (Не реальные данные):** Система **не должна** хранить реальные PAN (номера карт) и оригиналы паспортов. Только хэши/токены.
*   **Ограничение 2 (Продукт):** Поддерживается один продукт `prod_standard`: ставка 0.18, сумма 10k–1M, срок 3–60 мес., возраст 18–70, доход ≥ 30k. Корпоративные кредиты, групповые заявки — **не поддерживаются**.
*   **Ограничение 3 (Интеграции):** Система **не должна** напрямую инициировать платежи или переводы. Только принятие решения.

## 5. Пользовательские сценарии (Use Cases)

### Сценарий 1: Успешное одобрение
1. Клиент отправляет заявку (`POST /applications`).
2. Система валидирует данные (FR-02) и запрашивает БКИ (FR-03).
3. Скоринг возвращает score=90, dti=0.21, decision=APPROVED, amount_approved равен запрошенной сумме.
4. Система возвращает ответ клиенту и пишет аудит (FR-08).

### Сценарий 2: Отказ по низкому доходу
1. Клиент отправляет заявку: income=15000.
2. income=15000 < 30000 → `LOW_INCOME`; DTI=0.72 также высокий, но `LOW_INCOME` срабатывает раньше (правило №4, до правила №5 `HIGH_DTI`).
3. Скоринг возвращает decision=REFUSED, reason=LOW_INCOME.
4. Система возвращает отказ (схема `Decision`) и пишет аудит.
